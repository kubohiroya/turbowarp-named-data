Share data between extensions by name, not by copy.

Named Data is a shared contract and provider registry for unsandboxed TurboWarp extensions. One extension registers a provider for a namespace and kind; any other extension resolves namespace + name + kind + scope and receives metadata and a byte or stream body, without the payload ever passing through the registry.

Who uses it

Infrastructure for the other extensions.

Named Data has almost no blocks of its own. Its value is the registry that data-owning extensions share. Separately bundled extensions find the same registry through the stable key Symbol.for('@kubohiroya/turbowarp-named-data/registry'), so load order and bundling do not split it.

Asset Cache

Publishes named image, audio, and text assets as the asset kind.

Structured Data

Publishes JSON and YAML values as the structured kind, optionally with a schema identity.

Document Data

Publishes HTML and Markdown documents as the document kind.

Binary Data

Publishes raw bytes as the binary kind for other extensions to stream.

Kamishibai DSL 4.0 runtimes embed the side-effect-free composition entrypoint and join the same registry and lifecycle binding. Named Data does not add a separate member heading to the combined palette.

Quick start

Enable, load, check.

The registry is a startup-fixed feature that is off by default. The flag is read once when the bundle starts, so it must be set before the extension loads.

  1. Enable the feature flag

    In the host page, or in the editor's browser console for a quick test, set:

    globalThis.__TW_NAMED_DATA_FEATURE_FLAGS__ = {
  NAMED_DATA_REGISTRY_MVP: true
};

  2. Load the extension

    In TurboWarp, choose Add Extension → Custom Extension, use this file, and enable Run extension without sandbox:

    https://cdn.jsdelivr.net/npm/@kubohiroya/turbowarp-named-data@0.4.0/dist/named-data.js

  3. Check availability

    The single Boolean block confirms that the shared registry was installed.

    if <named data registry available?> then
  say [ready]
With the flag off, the palette is empty. The extension then publishes neither the registry service nor the availability block. This is the intended rollback state, not an error.

How it works

The registry routes; providers own the data.

The registry keeps only provider registrations, keyed by (namespace, kind), and the release callbacks of bodies that are currently open. Payload, storage, and caching stay inside each provider.

What a reference contains

FieldValuesMeaning
namespace Lowercase, starts with a letter, up to 64 of a-z 0-9 . - Logical ownership domain. Providers of different kinds may share one namespace.
name Provider-defined string The value's name inside the namespace.
kind structured, document, binary, asset Data type. Together with the namespace it selects the provider.
scope target, project Target scope needs a target identity; project scope needs a project identity. One is never substituted for the other.
schemaRef (optional) {id, version} Structured references only. A stable schema ID and a complete SemVer version, never a schema body.

What a provider returns

Metadata

  • nativeRepresentation: how the provider stores it
  • representation: the form selected for this body
  • mediaType, optional byteLength and sha256- digest
  • revision: opaque; never parse or order it
  • replayable: whether the body can be read again

Body

  • Uint8Array or ReadableStream<Uint8Array>
  • Returned directly to the consumer, never stored in the registry
  • Borrowed: call release(reason) when finished
No inline payload anywhere. References, metadata, manifests, and fixtures must never contain bytes, base64, or data URLs. The registry validates metadata and both representations against the data kind.

Composition API

Provide and consume from your own extension.

Other packages import the side-effect-free ESM entrypoint. Importing it does not register a TurboWarp extension; it only exposes the contract, registry functions, and feature-flag declarations. 

pnpm add --save-exact @kubohiroya/turbowarp-named-data@0.4.0

Register a provider

import {
  installNamedDataRegistry,
  type NamedDataProvider
} from '@kubohiroya/turbowarp-named-data/composition';

const registry = installNamedDataRegistry(runtime);
const provider: NamedDataProvider = {
  namespace: 'com.example.notes',
  kind: 'document',
  canResolve: (ref, rep) => rep === 'markdown',
  stat: (ref, rep, ctx) => ({ /* metadata */ }),
  openBody: (ref, rep, ctx) => ({ /* metadata, body, release */ }),
  release: () => {}
};
const registration = registry.registerProvider(provider);

A second provider for the same (namespace, kind) fails with NAMED_DATA_PROVIDER_CONFLICT.

Resolve a reference

import {getNamedDataRegistry}
  from '@kubohiroya/turbowarp-named-data/composition';

const registry = getNamedDataRegistry(runtime);
const opened = await registry?.openBody(
  {namespace: 'com.example.notes', name: 'intro',
   kind: 'document', scope: 'project'},
  'markdown',
  {project: projectIdentity}
);
try {
  // read opened.body
} finally {
  await opened?.release('complete');
}

getNamedDataRegistry returns undefined when no registry is installed.

Lifecycle and schema identity

Stop cleans up; schemas are named, never guessed.

When the project stops

  1. Every open body handle is released.
  2. Session providers are unregistered and released.
  3. Persistent providers keep their registration and run clearSession().

Registrations are session-scoped unless registered with {lifetime: 'persistent'}. Release operations are idempotent, so a provider can safely be released more than once.

Optional schema references

Structured references may carry schemaRef: {id, version}, for example {id: 'com.example.profile', version: '1.2.0'}. The provider must return the exact same identity in its metadata. The registry transports the identity only; schema documents, validators, and JSON values remain the provider's and consumer's responsibility. Providers publish schema references only when the separate startup flag NAMED_DATA_SCHEMA_REF is enabled (default off).

There is no implicit version fallback. A mismatch fails with NAMED_DATA_SCHEMA_VERSION_MISMATCH. A consumer that has no identity reports NAMED_DATA_SCHEMA_NOT_FOUND; one that cannot resolve it reports NAMED_DATA_SCHEMA_UNRESOLVED.

Troubleshooting

When a reference does not resolve

The palette shows no blocks
NAMED_DATA_REGISTRY_MVP was not true when the bundle started. Set globalThis.__TW_NAMED_DATA_FEATURE_FLAGS__ first, then reload the editor and load the extension again. Changing the flag after loading has no effect.
The extension refuses to load
Named Data must run unsandboxed. Enable Run extension without sandbox in the custom extension dialog. Only load extension code you trust.
Two extensions see different registries
Both must use installNamedDataRegistry or getNamedDataRegistry on the same TurboWarp runtime. A private registry created inside one extension is not shared. If the symbol slot already holds an incompatible object, the call fails with NAMED_DATA_INVALID_REGISTRY.
A target-scoped reference fails in project context
Target scope requires context.target and project scope requires context.project. The registry reports NAMED_DATA_SCOPE_MISMATCH instead of substituting one for the other.
Data disappears after pressing stop
Session providers are released on PROJECT_STOP_ALL. Register long-lived providers with {lifetime: 'persistent'} and implement clearSession() to drop only per-run state.
